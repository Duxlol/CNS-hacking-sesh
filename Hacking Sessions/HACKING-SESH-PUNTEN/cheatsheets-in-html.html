Computer & Network Security — Hacking Session Cheatsheet (uitgebreide versie)[cite: 1]

Gebaseerd op jullie opgeloste oefeningen + algemene/aanpalende technieken voor varianten die nog niet aan bod kwamen (RSA, Diffie-Hellman, web-kwetsbaarheden, encodings, tooling).[cite: 1]

Leeswijzer: ✅ = bevestigd door jullie eigen testen.[cite: 1] 📘 = algemene, publiek gedocumenteerde techniek (nog niet zelf getest op deze specifieke server) — betrouwbare theorie, maar verifieer de details live.[cite: 1] Secties zijn zo opgebouwd dat je op "herkenning" kan zoeken (Ctrl+F) als je een opgavetekst voor je hebt.[cite: 1]

0. De meta-methodologie — stel dit jezelf bij ELKE opgave[cite: 1]

  1. Categorie op de site? (Stream Ciphers / Block Ciphers / Hashing / HMAC / Public-Key / Web...) → beperkt meteen de mogelijke aanvallen.[cite: 1]
  2. Wordt een sleutel/nonce/seed/IV hergebruikt tussen twee berichten? → two-time pad.[cite: 1]
  3. Encryptie zonder authenticatie (geen MAC/HMAC/signature)? → bit-flipping / malleability.[cite: 1]
  4. Kleine of voorspelbare sleutelruimte expliciet vermeld (bv. "20-bit", "standardised keys", "short password")? → brute force of meet-in-the-middle.[cite: 1]
  5. Zelfgeschreven/"home-made" hash of cipher (geen AES/SHA uit een standaardbibliotheek)? → waarschijnlijk omkeerbaar (XOR/shift/rotate zijn allemaal inverteerbaar).[cite: 1]
  6. Fingerprint/hash "afgekapt" of goedkoop opgeslagen ("we don't have enough space/money to store the full X")? → birthday-attack / collision.[cite: 1]
  7. Een JWT (drie base64url-delen, gescheiden door punten)? → decodeer, kijk naar alg, probeer alg=none of zwak secret.[cite: 1]
  8. Een signature/HMAC-header bij JSON? → kijk naar canonicalisatie/parsing-mismatch (dubbele keys, volgorde, witruimte, encoding).[cite: 1]
  9. Server vraagt je een "volgende code" te voorspellen? → hash chain, en let op raw bytes vs hex-string![cite: 1]
  10. RSA-achtige getallen (n, e, d, grote priemgetallen, modulus)? → zie §5 (RSA-aanvallen): kijk eerst naar de grootte van e en of n factoriseerbaar is.[cite: 1]
  11. Diffie-Hellman-parameters (g, p, publieke sleutels A/B)? → zie §5.2: is p klein/standaard? Is de subgroep klein?[cite: 1]
  12. Een URL met een parameter die een ID/pad/URL bevat, of een inlog-/sessiesysteem? → denk web-kwetsbaarheden (§6): IDOR, SSRF, path traversal, SQLi, open redirect.[cite: 1]
  13. Een onherkenbare blob tekst (letters+cijfers, of enkel hex, of == op het einde)? → zie §7 (encoding-herkenning) vóór je aan "echte crypto" denkt — soms is het gewoon base64/hex/rot13.[cite: 1]
  14. Timing-gevoelige foutmeldingen ("invalid password" vs "invalid username", of merkbaar tragere responses)? → denk aan timing attacks / oracle-aanvallen (§2.4, §6).[cite: 1]

1. Stream Cipher aanvallen[cite: 1]

1.1 Keystream/seed hergebruik → Two-time pad ✅[cite: 1]

Herkenning: twee berichten versleuteld met "dezelfde configuratie/seed/nonce".[cite: 1]

keystream = bytes(c ^ p for c, p in zip(ciphertext_known, plaintext_known))
flag = bytes(c ^ k for c, k in zip(ciphertext_secret, keystream))

Toegepast op: Replanting, Noncense.[cite: 1]

Variant — N berichten, allemaal met dezelfde keystream (klassiek "many-time pad"): 📘[cite: 1]
Als je 3+ ciphertexts met dezelfde keystream hebt zonder een volledig known-plaintext, kan je per bytepositie met frequentie-analyse werken: XOR elk paar ciphertexts (c1^c2 = p1^p2), en gok dat één van de plaintexts op die positie een spatie (0x20) is — spaties XOR'en met letters geven herkenbare patronen (hoofdletter↔kleine letter verschuiving).[cite: 1] Tool: python3 -m venv + xortool, of het CTF-klassieke "crib dragging".[cite: 1]

1.2 Zwakke PRNG / state recovery (custom LCG, enz.) ✅[cite: 1]

Zie je eigen uitgewerkte voorbeeld (Replanting).[cite: 1] Generaliseer: elke keer dat je een custom RNG ziet met gekende formule (next = (A*state + C) mod M, of een LFSR, of Mersenne Twister met voorspelbare seed zoals time.time()), probeer de interne state te reconstrueren uit gedeeltelijke output.[cite: 1]

  • Mersenne Twister (Python's random): als je 624 opeenvolgende 32-bit outputs ziet, kan je de volledige interne state klonen met tools als randcrack (pip install randcrack) en daarna toekomstige "willekeurige" waarden perfect voorspellen.[cite: 1]
  • Geseed met tijd (random.seed(int(time.time()))): brute force de seed over een klein tijdvenster rond het moment van de request.[cite: 1]

1.3 Malleability / bit-flipping (geen MAC) ✅[cite: 1]

Zie uitgewerkt voorbeeld (Secure Bank 1).[cite: 1] Kernformule:[cite: 1]

keystream = bytes(c ^ p for c, p in zip(ciphertext, known_plaintext))
new_ciphertext = bytes(k ^ p for k, p in zip(keystream, new_desired_plaintext))

Let op: keystream hangt af van nonce — blijf binnen dezelfde sessie werken.[cite: 1]

Variant — CTR-counter manipulatie: 📘 bij AES-CTR kan je, als je de counter/nonce-opbouw kent, ook blokken van positie laten wisselen door de counter-waarde in de ciphertext-aanvraag te forceren naar een waarde die al elders gebruikt is (vergelijkbaar met nonce-reuse, maar dan actief uitgelokt in plaats van toevallig).[cite: 1]

1.4 RC4-specifieke zwaktes 📘[cite: 1]

Als je ooit RC4 tegenkomt: de eerste paar keystream-bytes zijn statistisch niet uniform willekeurig (bekende bias in byte 0 en 1).[cite: 1] Bij hergebruikte/voorspelbare sleutels (WEP-stijl) kan je met voldoende samples de sleutel herleiden (FMS-attack, KoreK-attacks).[cite: 1] Tool: aircrack-ng als het om WEP gaat.[cite: 1]

2. Block Cipher aanvallen[cite: 1]

2.1 Kleine/voorspelbare sleutelruimte → brute force ✅[cite: 1]

Zie Key Standardisation.[cite: 1] Probeer sleutels afgeleid van bekende strings (naam, namespace, bedrijfsnaam), met padding-varianten (nullen vooraan/achteraan, herhaling, hoofdletters/kleine letters), en brute force resterende onbekende tekens als die beperkt zijn.[cite: 1]

2.2 Double/meervoudige encryptie → Meet-in-the-Middle ✅[cite: 1]

Zie AES 2 demo.[cite: 1] Enc(K1,P) = Dec(K2,C) → bouw een hashtabel voor alle K1, zoek voor elke K2.[cite: 1]

table = {}
for k1 in range(2**20):
    table[AES_encrypt(make_key(k1), P)] = k1
for k2 in range(2**20):
    mid = AES_decrypt(make_key(k2), C)
    if mid in table:
        print("K1 =", table[mid], "K2 =", k2)

Vereist een bekend (plaintext-blok, ciphertext-blok)-paar van hetzelfde blok (bestandsheaders zijn goud: BMP "BM", PNG \x89PNG, JPEG \xFF\xD8\xFF, ZIP PK\x03\x04, PDF %PDF-, GIF GIF89a).[cite: 1]

2.4 CBC Padding Oracle Attack 📘[cite: 1]

Herkenning: CBC-mode, en de server geeft een ander soort foutmelding (of merkbaar ander gedrag/timing) bij "invalid padding" versus "valid padding maar ongeldige data".[cite: 1]

Principe (kort): PKCS#7-padding betekent dat de laatste bytes van het plaintext aangeven hoeveel paddingbytes er zijn (bv. laatste byte 0x04 → de laatste 4 bytes moeten allemaal 0x04 zijn).[cite: 1] Door de voorlaatste ciphertext-blok byte per byte te wijzigen en te kijken of de server "padding OK" of "padding FOUT" zegt, kan je elke byte van het plaintext achterhalen — zonder de sleutel te kennen, puur via dat ja/nee-signaal.[cite: 1] Je werkt van de laatste byte van een blok naar de eerste.[cite: 1]

# Zeer vereenvoudigd skelet — pas de oracle-functie aan je server aan
def padding_oracle(iv_block, cipher_block):
    # stuur iv_block + cipher_block naar de server, return True als "padding valid"
    ...

def decrypt_block(prev_block, target_block):
    intermediate = bytearray(16)
    plaintext = bytearray(16)
    for pad_val in range(1, 17):
        pos = 16 - pad_val
        fake_prev = bytearray(16)
        for i in range(pos+1, 16):
            fake_prev[i] = intermediate[i] ^ pad_val
        for guess in range(256):
            fake_prev[pos] = guess
            if padding_oracle(bytes(fake_prev), target_block):
                intermediate[pos] = guess ^ pad_val
                plaintext[pos] = intermediate[pos] ^ prev_block[pos]
                break
    return bytes(plaintext)

Bron: https://robertheaton.com/2013/07/29/padding-oracle-attack/ · tool: padbuster.[cite: 1]

2.5 Related-key / weak-key varianten (DES-specifiek) 📘[cite: 1]

DES heeft 4 bekende zwakke sleutels (en 12 semi-zwakke) waarbij encryptie = decryptie (self-inverse).[cite: 1] Als een opgave specifiek over "DES weak keys" gaat: zoek op *"DES weak keys list"* — er zijn er maar 4, triviaal te proberen.[cite: 1]

3. Hash-functie aanvallen[cite: 1]

3.1 Zelfgeschreven ("home-made") hash → omkeren ✅[cite: 1]

Zie Better Hash.[cite: 1] Keer rondevolgorde + stapvolgorde om, vervang elke operatie door haar inverse (XOR↔XOR, rol↔ror, prefix-XOR-ketting loop je van hoog naar laag, lijstrotatie omgekeerd).[cite: 1]

3.2 Afgekapte hash / fingerprint → Birthday-attack ✅[cite: 1]

Zie Secure Bank 2.[cite: 1] Met *n*-bit afgekapte hash vind je een collision in ~2^(n/2) pogingen i.p.v. 2^n.[cite: 1]

3.3 Hash chain voorspellen ✅[cite: 1]

Zie Space Race 1.[cite: 1] Hash de ruwe bytes, niet de hex-tekst: bytes.fromhex(code), niet code.encode().[cite: 1]

3.4 Hash length-extension attack 📘[cite: 1]

Herkenning: een MAC geconstrueerd als hash(secret || message) (géén echte HMAC) met MD5/SHA-1/SHA-256 (Merkle–Damgård-constructies zijn hier kwetsbaar aan, SHA-3/BLAKE2 niet).[cite: 1] Je kent hash(secret||message) en de lengte van message, maar niet secret zelf — en je wil data achteraan toevoegen met een geldige nieuwe hash.[cite: 1]

pip install hlextend --break-system-packages
import hlextend
sha = hlextend.new('sha256')  # of 'sha1', 'md5'
new_hash = sha.extend(
    data=b";admin=true",          # wat je wil toevoegen
    secret=b"origineel_bericht",  # het bericht zoals jij het kent (zonder secret)
    secret_length=16,             # GOK/brute-force de lengte van de geheime sleutel (probeer 1..64)
    hexdigest="originele_mac_hex"
)
new_message = sha.hexdigest()     # dit stuur je ipv het origineel, met new_hash als MAC

Belangrijkste denkstap: als je de secret-lengte niet kent, loop je gewoon over een plausibel bereik (1 t.e.m. 32 of 64 bytes) en probeer je elke new_message/new_hash-combinatie tot de server er één accepteert.[cite: 1]

4. Authenticatie-protocollen & MAC's[cite: 1]

4.1 HTTP/RTSP Digest Authentication — offline dictionary attack ✅[cite: 1]

Geen print() per poging in de loop — dat maakt het uren trager.[cite: 1]

4.2 JWT-aanvallen — alg: none ✅[cite: 1]

Zie Token of Trust: decodeer header+payload, alg→none, rechten verhogen, her-encoderen, signature-deel leeg laten, versturen als Authorization: Bearer <token>.[cite: 1]

Andere JWT-varianten om te proberen als alg=none niet werkt: 📘[cite: 1]

  • Zwak/geraden HS256-secret → jwt_tool of hashcat -m 16500 -a 0 token.txt rockyou.txt.[cite: 1]
  • kid-header injectie / algorithm confusion (RS256→HS256) als de server per ongeluk een publieke sleutel als HMAC-secret hergebruikt.[cite: 1]
  • Ontbrekende exp-check → een oud/verlopen token blijft gewoon geldig.[cite: 1]
  • jku/x5u-header die naar een URL wijst die jij kan controleren (server haalt daar de verificatiesleutel op).[cite: 1]

4.3 HMAC / signature-aanvallen op JSON — duplicate-key confusion ✅[cite: 1]

Zie Signed, Sealed, Misinterpreted: hergebruik een legitieme signature, stuur een rauwe string (geen Python-dict, want die kan geen dubbele keys hebben) met een key (bv. "role") twee keer, in de hoop dat de signature-check en de autorisatielogica elk een andere van de twee waarden gebruiken.[cite: 1]

Generaliseer naar andere parsing-mismatches: 📘[cite: 1]

  • Unicode-tricks: "r\u006fle" (unicode-escape voor 'o') kan door de ene parser anders behandeld worden dan door de andere.[cite: 1]
  • Extra/onverwachte velden: soms valideert de signature-check enkel een subset van velden, en kan je extra velden toevoegen die de autorisatielogica wel leest.[cite: 1]
  • Content-Type verwarring: dezelfde data als application/json vs application/x-www-form-urlencoded versturen kan soms een andere parser triggeren aan de serverkant.[cite: 1]
  • Timing-attack op MAC-vergelijking: als een server MAC's vergelijkt met een niet-constant-time == (i.p.v. hmac.compare_digest), kan je in theorie byte per byte raden via responstijd — zelden praktisch haalbaar binnen een CTF-sessie, maar wel een herkenbaar concept.[cite: 1]

5. Public-key cryptografie (RSA, Diffie-Hellman, ECC) 📘[cite: 1]

(Nog niet gezien in jullie opgaves, maar hoort standaard bij dit vak — hieronder de meest voorkomende CTF-klassiekers.)[cite: 1]

5.1 RSA-aanvallen[cite: 1]

RSA: publieke sleutel (n, e), privé d, met n = p*q (2 grote priemgetallen).[cite: 1] Versleutelen: c = m^e mod n.[cite: 1] Herken welke situatie van toepassing is:[cite: 1]

Twee verschillende ciphertexts met dezelfde modulus n, verschillende e1/e2 (vaak co-priem)[cite: 1]Common modulus attack — met extended Euclidean algorithm a*e1 + b*e2 = 1 vinden, dan m = c1^a * c2^b mod n[cite: 1]

5.2 Diffie-Hellman-aanvallen[cite: 1]

Standaard DH: beide partijen kiezen geheim a/b, delen A = g^a mod p, B = g^b mod p, gedeelde sleutel g^(ab) mod p.[cite: 1]

  • Kleine of bekende p: als p klein genoeg is (< ~60 bits), is het discrete-log-probleem (a vinden uit A = g^a mod p) gewoon brute-forceerbaar of met Pollard's rho / baby-step-giant-step op te lossen (sympy.discrete_log(p, A, g)).[cite: 1]
  • Kleine subgroep-aanval: als p-1 veel kleine priemfactoren heeft, kan de geheime exponent mod die kleine factoren gelekt worden (Pohlig-Hellman-algoritme).[cite: 1]
  • Logjam-stijl aanval (bekende/herbruikte standaard-p-waarden van 512-1024 bit): zoek op *"logjam attack precomputation"*.[cite: 1]
  • MITM zonder authenticatie: als DH niet aan een signature/certificaat gekoppeld is, kan een attacker tussen beide partijen eigen g^x-waarden insturen.[cite: 1]

5.3 ECDSA / digitale handtekeningen — nonce-hergebruik[cite: 1]

Als twee verschillende berichten dezelfde "random" nonce k gebruiken bij ECDSA-signing (klassieke implementatiefout, net als bij stream ciphers!), kan je daaruit de privésleutel herleiden met simpele modulaire rekenkunde.[cite: 1] Herkenning: twee signatures met dezelfde r-waarde.[cite: 1] Zoek op *"ECDSA nonce reuse attack"* — exact dezelfde "hergebruik-logica" als jullie stream cipher-opgaves, maar dan op een ander wiskundig niveau.[cite: 1]

12. Custom rotor-/machine-cijfers (zoals "My First Enigma Machine") ✅[cite: 1]

Herkenning: de opgave beschrijft in woorden een EIGEN, volledig custom "machine" (géén bestaande, opzoekbare cipher) met alfabetten/rotoren die na elke letter roteren, waarbij een volgende rotor pas draait als de vorige een volledige cyclus gemaakt heeft (klassiek "odometer"-mechanisme, zoals de echte Enigma).[cite: 1] Dit kan je nergens opzoeken — je MOET het zelf simuleren en programmeren.[cite: 1] Precies het soort vraag waar de docent op doelde met "net niet op te zoeken".[cite: 1]

De sleutel tot dit type opgave[cite: 1]

Bij een "zuivere" rotor-machine (zonder reflector/plugboard) hangt de rotatie van elke rotor enkel af van hoeveel letters al verwerkt zijn — niet van de inhoud van het bericht.[cite: 1] Dat betekent:[cite: 1]

  1. Je kan de rotor-standen voor élke positie voorberekenen, los van wat het plaintext/ciphertext is.[cite: 1]
  2. Elke stap is gewoon een substitutie (permutatie) — en permutaties zijn altijd omkeerbaar met .index() in plaats van rotor[index].[cite: 1]
  3. Decrypteren = de pijplijn in omgekeerde volgorde doorlopen, met .index() i.p.v. direct indexeren, bij elke rotor.[cite: 1]

Bevestigd opgelost voorbeeld[cite: 1]

Opgave: 3 rotoren (MACHINEBDFGJKLOPQRSTUVWXYZ, ORBITACDEFGHJKLMNPQSUVWXYZ, CIPHERABDFGJKLMNOQSTUVWXYZ), Rotor 1 roteert elke letter, Rotor 2 roteert als Rotor 1 een volledige cyclus (26 letters) gemaakt heeft, Rotor 3 als Rotor 2 een volledige cyclus gemaakt heeft.[cite: 1] Geen reflector (1 richting).[cite: 1]
Ciphertext HKV{BSBU-B-SJYZNNB-DNFW-IXH-YTA-RPL-RTXOLWFQ} → CNS{JOHN-F-KENNEDY-SAID-ICH-BIN-EIN-BERLINER}.[cite: 1]
Volledig werkend script: 18_custom_rotor_cipher_enigma.py.[cite: 1]

0. De meta-methodologie — stel dit jezelf bij ELKE opgave[cite: 2]

  1. Categorie op de site? (Stream Ciphers / Block Ciphers / Hashing / HMAC / Public-Key / Web...) → beperkt meteen de mogelijke aanvallen.[cite: 2]
  2. Wordt een sleutel/nonce/seed/IV hergebruikt tussen twee berichten? → two-time pad.[cite: 2]
  3. Encryptie zonder authenticatie (geen MAC/HMAC/signature)? → bit-flipping / malleability.[cite: 2]
  4. Kleine of voorspelbare sleutelruimte expliciet vermeld (bv. "20-bit", "standardised keys", "short password")? → brute force of meet-in-the-middle.[cite: 2]
  5. Zelfgeschreven/"home-made" hash of cipher (geen AES/SHA uit een standaardbibliotheek)? → waarschijnlijk omkeerbaar (XOR/shift/rotate zijn allemaal inverteerbaar).[cite: 2]
  6. Fingerprint/hash "afgekapt" of goedkoop opgeslagen ("we don't have enough space/money to store the full X")? → birthday-attack / collision.[cite: 2]
  7. Een JWT (drie base64url-delen, gescheiden door punten)? → decodeer, kijk naar alg, probeer alg=none of zwak secret.[cite: 2]
  8. Een signature/HMAC-header bij JSON? → kijk naar canonicalisatie/parsing-mismatch (dubbele keys, volgorde, witruimte, encoding).[cite: 2]
  9. Server vraagt je een "volgende code" te voorspellen? → hash chain, en let op raw bytes vs hex-string![cite: 2]
  10. RSA-achtige getallen (n, e, d, grote priemgetallen, modulus)? → zie §5 (RSA-aanvallen): kijk eerst naar de grootte van e en of n factoriseerbaar is.[cite: 2]
  11. Diffie-Hellman-parameters (g, p, publieke sleutels A/B)? → zie §5.2: is p klein/standaard? Is de subgroep klein?[cite: 2]
  12. Een URL met een parameter die een ID/pad/URL bevat, of een inlog-/sessiesysteem? → denk web-kwetsbaarheden (§6): IDOR, SSRF, path traversal, SQLi, open redirect.[cite: 2]
  13. Een onherkenbare blob tekst (letters+cijfers, of enkel hex, of == op het einde)? → zie §7 (encoding-herkenning) vóór je aan "echte crypto" denkt — soms is het gewoon base64/hex/rot13.[cite: 2]
  14. Timing-gevoelige foutmeldingen ("invalid password" vs "invalid username", of merkbaar tragere responses)? → denk aan timing attacks / oracle-aanvallen (§2.4, §6).[cite: 2]

1. Stream Cipher aanvallen[cite: 2]

1.1 Keystream/seed hergebruik → Two-time pad ✅[cite: 2]

Herkenning: twee berichten versleuteld met "dezelfde configuratie/seed/nonce".[cite: 2]

keystream = bytes(c ^ p for c, p in zip(ciphertext_known, plaintext_known))
flag = bytes(c ^ k for c, k in zip(ciphertext_secret, keystream))

Toegepast op: Replanting, Noncense.[cite: 2]

Variant — N berichten, allemaal met dezelfde keystream (klassiek "many-time pad"): 📘[cite: 2]
Als je 3+ ciphertexts met dezelfde keystream hebt zonder een volledig known-plaintext, kan je per bytepositie met frequentie-analyse werken: XOR elk paar ciphertexts (c1^c2 = p1^p2), en gok dat één van de plaintexts op die positie een spatie (0x20) is — spaties XOR'en met letters geven herkenbare patronen (hoofdletter↔kleine letter verschuiving).[cite: 2] Tool: python3 -m venv + xortool, of het CTF-klassieke "crib dragging".[cite: 2]

1.2 Zwakke PRNG / state recovery (custom LCG, enz.) ✅[cite: 2]

Zie je eigen uitgewerkte voorbeeld (Replanting).[cite: 2] Generaliseer: elke keer dat je een custom RNG ziet met gekende formule (next = (A*state + C) mod M, of een LFSR, of Mersenne Twister met voorspelbare seed zoals time.time()), probeer de interne state te reconstrueren uit gedeeltelijke output.[cite: 2]

  • Mersenne Twister (Python's random): als je 624 opeenvolgende 32-bit outputs ziet, kan je de volledige interne state klonen met tools als randcrack (pip install randcrack) en daarna toekomstige "willekeurige" waarden perfect voorspellen.[cite: 2]
  • Geseed met tijd (random.seed(int(time.time()))): brute force de seed over een klein tijdvenster rond het moment van de request.[cite: 2]

1.3 Malleability / bit-flipping (geen MAC) ✅[cite: 2]

Zie uitgewerkt voorbeeld (Secure Bank 1).[cite: 2] Kernformule:[cite: 2]

keystream = bytes(c ^ p for c, p in zip(ciphertext, known_plaintext))
new_ciphertext = bytes(k ^ p for k, p in zip(keystream, new_desired_plaintext))

Let op: keystream hangt af van nonce — blijf binnen dezelfde sessie werken.[cite: 2]

Variant — CTR-counter manipulatie: 📘 bij AES-CTR kan je, als je de counter/nonce-opbouw kent, ook blokken van positie laten wisselen door de counter-waarde in de ciphertext-aanvraag te forceren naar een waarde die al elders gebruikt is (vergelijkbaar met nonce-reuse, maar dan actief uitgelokt in plaats van toevallig).[cite: 2]

1.4 RC4-specifieke zwaktes 📘[cite: 2]

Als je ooit RC4 tegenkomt: de eerste paar keystream-bytes zijn statistisch niet uniform willekeurig (bekende bias in byte 0 en 1).[cite: 2] Bij hergebruikte/voorspelbare sleutels (WEP-stijl) kan je met voldoende samples de sleutel herleiden (FMS-attack, KoreK-attacks).[cite: 2] Tool: aircrack-ng als het om WEP gaat.[cite: 2]

2.4 CBC Padding Oracle Attack 📘[cite: 2]

Herkenning: CBC-mode, en de server geeft een ander soort foutmelding (of merkbaar ander gedrag/timing) bij "invalid padding" versus "valid padding maar ongeldige data".[cite: 2]

Principe (kort): PKCS#7-padding betekent dat de laatste bytes van het plaintext aangeven hoeveel paddingbytes er zijn (bv. laatste byte 0x04 → de laatste 4 bytes moeten allemaal 0x04 zijn).[cite: 2] Door de voorlaatste ciphertext-blok byte per byte te wijzigen en te kijken of de server "padding OK" of "padding FOUT" zegt, kan je elke byte van het plaintext achterhalen — zonder de sleutel te kennen, puur via dat ja/nee-signaal.[cite: 2] Je werkt van de laatste byte van een blok naar de eerste.[cite: 2]

# Zeer vereenvoudigd skelet — pas de oracle-functie aan je server aan
def padding_oracle(iv_block, cipher_block):
    # stuur iv_block + cipher_block naar de server, return True als "padding valid"
    ...

def decrypt_block(prev_block, target_block):
    intermediate = bytearray(16)
    plaintext = bytearray(16)
    for pad_val in range(1, 17):
        pos = 16 - pad_val
        fake_prev = bytearray(16)
        for i in range(pos+1, 16):
            fake_prev[i] = intermediate[i] ^ pad_val
        for guess in range(256):
            fake_prev[pos] = guess
            if padding_oracle(bytes(fake_prev), target_block):
                intermediate[pos] = guess ^ pad_val
                plaintext[pos] = intermediate[pos] ^ prev_block[pos]
                break
    return bytes(plaintext)

Zie Space Race 1.[cite: 2] Hash de ruwe bytes, niet de hex-tekst: bytes.fromhex(code), niet code.encode().[cite: 2]

3.4 Hash length-extension attack 📘[cite: 2]

Herkenning: een MAC geconstrueerd als hash(secret || message) (géén echte HMAC) met MD5/SHA-1/SHA-256 (Merkle–Damgård-constructies zijn hier kwetsbaar aan, SHA-3/BLAKE2 niet).[cite: 2] Je kent hash(secret||message) en de lengte van message, maar niet secret zelf — en je wil data achteraan toevoegen met een geldige nieuwe hash.[cite: 2]

import hlextend
sha = hlextend.new('sha256')  # of 'sha1', 'md5'
new_hash = sha.extend(
    data=b";admin=true",          # wat je wil toevoegen
    secret=b"origineel_bericht",  # het bericht zoals jij het kent (zonder secret)
    secret_length=16,             # GOK/brute-force de lengte van de geheime sleutel (probeer 1..64)
    hexdigest="originele_mac_hex"

5.2 Diffie-Hellman-aanvallen[cite: 2]

Standaard DH: beide partijen kiezen geheim a/b, delen A = g^a mod p, B = g^b mod p, gedeelde sleutel g^(ab) mod p.[cite: 2]

  • Kleine of bekende p: als p klein genoeg is (< ~60 bits), is het discrete-log-probleem (a vinden uit A = g^a mod p) gewoon brute-forceerbaar of met Pollard's rho / baby-step-giant-step op te lossen (sympy.discrete_log(p, A, g)).[cite: 2]
  • Kleine subgroep-aanval: als p-1 veel kleine priemfactoren heeft, kan de geheime exponent mod die kleine factoren gelekt worden (Pohlig-Hellman-algoritme).[cite: 2]
  • Logjam-stijl aanval (bekende/herbruikte standaard-p-waarden van 512-1024 bit): zoek op *"logjam attack precomputation"*.[cite: 2]
  • MITM zonder authenticatie: als DH niet aan een signature/certificaat gekoppeld is, kan een attacker tussen beide partijen eigen g^x-waarden insturen.[cite: 2]

5.3 ECDSA / digitale handtekeningen — nonce-hergebruik[cite: 2]

Als twee verschillende berichten dezelfde "random" nonce k gebruiken bij ECDSA-signing (klassieke implementatiefout, net als bij stream ciphers!), kan je daaruit de privésleutel herleiden met simpele modulaire rekenkunde.[cite: 2] Herkenning: twee signatures met dezelfde r-waarde.[cite: 2] Zoek op *"ECDSA nonce reuse attack"* — exact dezelfde "hergebruik-logica" als jullie stream cipher-opgaves, maar dan op een ander wiskundig niveau.[cite: 2]

Stream Ciphers & Bit-Flipping Cheat Sheet[cite: 3]

Basisprincipes van Stream Ciphers (XOR Regels)[cite: 3]

Een stream cipher genereert een pseudo-willekeurige stroom van bits (de Keystream) op basis van een sleutel (en vaak een Nonce/IV).[cite: 3] De versleuteling gebeurt door de Keystream te XOR'en met de Plaintext.[cite: 3]

  • Versleutelen: Ciphertext = Plaintext ⊕ Keystream[cite: 3]
  • Ontsleutelen: Plaintext = Ciphertext ⊕ Keystream[cite: 3]
  • Keystream achterhalen (Known-Plaintext): Keystream = Ciphertext ⊕ Plaintext[cite: 3]

De Wiskunde van een Bit-Flipping Aanval[cite: 3]

Als je de originele plaintext kent (of deels kan raden), kan je de ciphertext manipuleren zodat deze na ontsleuteling door de server in jouw gewenste tekst verandert, zonder dat je de geheime sleutel nodig hebt.[cite: 3]

Methode 1: Via de Keystream (2 stappen)[cite: 3]

Dit is de methode die in je script werkte.[cite: 3]

  1. Vind de Keystream: XOR de originele ciphertext met de bekende originele plaintext.
    K = C ⊕ Poud[cite: 3]
  2. Maak de nieuwe Ciphertext: XOR jouw nieuwe (vervalste) plaintext met de gevonden Keystream.
    Cnieuw = Pnieuw ⊕ K[cite: 3]

Methode 2: Directe XOR (1 stap)[cite: 3]

Omdat XOR associatief en commutatief is, kan je de bovenstaande stappen ook combineren tot één formule:[cite: 3]

  • Cnieuw = C ⊕ Poud ⊕ Pnieuw[cite: 3]

(In Python: bytes(c ^ p_old ^ p_new for c, p_old, p_new in zip(ciphertext, old_plaintext, new_plaintext)))[cite: 3]

Eigenschappen van XOR (Waarom dit werkt)[cite: 3]

  • A ⊕ A = 0 (Iets XOR'en met zichzelf is nul)[cite: 3]
  • A ⊕ 0 = A (Iets XOR'en met nul verandert niets)[cite: 3]
  • A ⊕ B ⊕ A = B (Als je twee keer met hetzelfde XOR't, hef je het op)[cite: 3]

Cruciale Aandachtspunten voor Oefeningen[cite: 3]

  • Exacte lengte: XOR werkt bit per bit.[cite: 3] Jouw Poud en Pnieuw moeten exact even lang zijn in bytes.[cite: 3]
  • Data formaten: Let goed op verborgen spaties of tekens.[cite: 3] Bij JSON voegt Python's json.dumps() vaak een spatie toe na een dubbele punt ("amount": "100" in plaats van "amount":"100").[cite: 3] Eén byte verschil verschuift de hele berekening.[cite: 3]
  • Nonce/IV: Vaak worden de eerste bytes van de raw data gebruikt als Nonce of Initialization Vector.[cite: 3] Deze mag je niet mee-XOR'en in je bit-flipping berekening, maar moet je wel ongewijzigd terugsturen voor de gemanipuleerde ciphertext.[cite: 3]
  • Byte manipulatie in Python: Gebruik zip() correct.[cite: 3] Zorg dat je iterators even lang zijn en dat je bytes met bytes XOR't.[cite: 3] Gebruik bytes.fromhex() en .hex().encode() om te wisselen tussen netwerkpayloads en wiskundige bewerkingen.[cite: 3]
